# Export / import (backup files) and the 8→9 database recreate

Covers the JSON backup format and everything that rides in it (rules, groups, usage history, app settings),
the per-entry failure policy, the Strict Mode gate on importing weaker settings, and the one Room migration
that is not an `ALTER TABLE`, because it rewrites the same `usage_events` rows a backup carries.
**Read before touching `data/export/`, `ImportRulesUseCase`, `NudgePreferences.applyImportedSettings`, or `MIGRATION_8_9`.**

## Export/Import architecture

- `data/export/RuleExportData.kt` — data classes: `NudgeExport`, `ExportedRule`, `ExportedGroup`, `ExportedHistoryEvent`, `ExportedSettings`
- `data/export/RuleExporter.kt` — serialization/deserialization via `org.json` (no extra dependency). Handles null fields, version validation, block mode validation. `@Singleton` with `@Inject`.
- `domain/usecase/ExportRulesUseCase.kt` — collects EVERY rule with its `enabled` flag (see below) + groups + members + the full usage history + the app's settings, delegates to RuleExporter (off the main thread)
- `domain/usecase/ImportRulesUseCase.kt` — `preview()` (suspend) returns an `ImportPreview`, `execute()` inserts with duplicate detection (packageName + mode + schedule match). Creates groups by name if missing. Applies the file's settings, if it carries any, then merges history last.
- UI: `ui/backup/` owns every entry point — `BackupViewModel` (the only holder of the two use cases), `rememberBackupActions` (the two document pickers) and `BackupDialogs` (preview / result / error / save-result / Strict Mode challenge), plus `ImportMessages.kt`'s pure text builders. Two screens host that pair: the three-dot overflow menu in `ActiveRulesScreen` and the "Backup" section in `SettingsScreen`. Both offer **Save backup** (`ACTION_CREATE_DOCUMENT`), **Share backup** (`ACTION_SEND` via FileProvider) and **Import backup** (`ACTION_OPEN_DOCUMENT`), with a confirmation dialog before importing.
- Export format: pretty-printed JSON, version 1, human-readable. Groups referenced by name (not ID). Usage history and app settings both ride in the same file — see below.

### Every rule, including the ones switched off (issue #43)

The export collected `getEnabledRules()`, so a rule the user had switched off — how people park a rule they mean to come back to — was absent from their backup and lost on a restore to a wiped phone. It now collects `getAllRules()`.

- **Nothing about the FORMAT changed.** `enabled` has always been written for every exported rule and `parseRule` has always read it, defaulting to `true`. That default is the backward-compatibility mechanism and must stay: a pre-#43 file names no flag *and only ever contained enabled rules*, so reading its silence as "off" would restore a phone that blocks nothing. Still envelope version 1 in both directions, for the same reason `history` and `settings` are.
- **Duplicate detection does not consider `enabled`** (target + mode + schedule), so re-importing a backup onto a device that already has the rule does not flip its switch — a duplicate is a rule you already have, not an instruction about its state.
- Pinned by `ExportRulesUseCaseTest` (the collection: `getEnabledRules` is deliberately left unstubbed, so reaching for it fails loudly) and two `ImportRulesUseCaseTest` cases (the off-backup-restore round trip through the real exporter, and an old file with no `enabled` key restoring switched ON).

### Saving a backup to the device (`ACTION_CREATE_DOCUMENT`)

Export used to fire `ACTION_SEND` only, and **"save to device" is not an `ACTION_SEND` target on Android**: enumerated on the Pixel 3, the entire share sheet was Drive, Gmail, KDE Connect, Telegram, Bitwarden and Discord — every one of them sending the file to a cloud or another device. A zero-internet-permission privacy app could not put a backup in its own user's Downloads folder, and the file the share path writes lives in `cacheDir`, where the system may evict it.

- **Save** uses the `CreateDocument("application/json")` contract, mirroring the `OpenDocument` import, and writes through the returned `Uri` in mode **`"wt"`**. `"w"` does not truncate on every provider: overwriting a larger previous backup would leave its tail behind and produce a file that is no longer valid JSON — a corrupt backup that looks saved.
- **A refused write is reported as a failure**, not as nothing. A backup the user believes they have is worse than one they know they do not.
- **The export runs only once a destination exists.** Serializing an unbounded history is real work, so backing out of the picker costs nothing.
- Files are offered as `nudge-backup-<ISO date>.json` (`ui/backup/BackupFileName.kt`, pure and unit-tested) so a folder of backups sorts and identifies itself.
- **Share stays**, as the second option: sending the file straight to another device or a password manager is legitimate, it just cannot be the only destination.

### Why backup has its own ViewModel

Backup lived in `ActiveRulesViewModel`, reachable only from that screen's overflow menu — and Active Rules is itself reachable only by tapping a dashboard stat card. A QA agent searching exhaustively concluded the feature did not exist (`docs/BACKLOG.md`, v1.12.0 QA). Adding the Settings entry point by copying the flow would have meant a second, independent idea of what a weakening import owes Strict Mode, so the flow moved into `ui/backup/BackupViewModel` instead and both screens host the same instance-per-screen of it. Settings also gets backup without dragging in the installed-app scan and rules flow `ActiveRulesViewModel` exists for.

`BackupEntryPointsContractTest` pins the shape rather than the list: both screens still offer all three actions, **every** screen that wires `rememberBackupActions` also renders `BackupDialogs` (a picker with no dialogs shows the user nothing after an import, including no challenge), and only `BackupViewModel` touches the export/import use cases.

### Usage HISTORY rides in the same file (optional `history` key, still version 1)

An export carries the `usage_events` rows behind the home tiles and both insight pages, so a device move keeps a user's "Blocked 19 / Walked Away 7" instead of resetting them to zero. `ExportedHistoryEvent` is a `UsageEvent` minus its row id: packageName, timestamp, wasBlocked, blockMode, userChangedMind. **Screen time is deliberately NOT in scope** — it comes from `UsageStatsManager`, is OS-owned, and re-derives on whatever device the file lands on.

- **Still envelope `version: 1`, and that was verified rather than assumed.** Every shipped importer reads the envelope by KNOWN KEY ONLY (`version`, then `rules`/`groups` via `optJSONArray`) — checked back to the original `ec893ab` exporter — so an unknown top-level key has never been able to fail an import. A bump to version 2 would instead make every older Nudge reject the whole file (`"newer than supported"`) and cost the user their RULES in order to deliver history that build cannot use. **Device-verified on the shipped v1.13.0 (vc41) release build**: importing a hand-written file carrying `history` + `someOtherFutureKey` produced the normal "Import 1 rule(s)?" dialog with no error. `HistoryExportTest."unknown top-level keys are ignored…"` is the forward guard.
- **Export is always-on (no toggle), and the history array is written COMPACTLY** inside the otherwise pretty-printed file. `RuleExporter.spliceHistory` appends `"history": [...]` as the last member by index-of-`}` arithmetic (order-independent — Android's org.json preserves insertion order, the desktop one the unit tests use does not), and `appendHistoryArray` writes straight into the `StringBuilder` via `JSONObject.quote` instead of materialising a `JSONArray` of `JSONObject`s. Retention is not enforced anywhere (`UsageRepository.cleanup` still has no call site), so the row count is unbounded: ~100 bytes/event compact vs 4-5x pretty, and no 50k-object graph on a 3GB device. Everything on this path — export serialization, import parse, the file read in the picker callback, and the cache-file write behind the share intent — moved OFF the main thread for the same reason.
- **Import MERGES, never replaces.** `data/export/HistoryMerge` (pure) is the whole policy. Dedup key is `UsageEventKey` = (packageName, timestamp, wasBlocked, userChangedMind). The row id is excluded — it is the exporting device's private business, and including it would duplicate everything on any phone that already has history. **blockMode is also excluded**: it is descriptive, not identifying, and keying on it would let a mode rename duplicate a user's entire history. `userChangedMind` IS in the key, because a walk-away writes a SECOND row for the same confrontation milliseconds after the first (see "The walk-away path" in `block-overlay-lifecycle.md`) — collapsing those two would break the Blocked-vs-Walked-Away tiles. Duplicates WITHIN one file are kept deliberately (the source device really had two rows); idempotency does not depend on collapsing them, since on a second import both are already stored.
- **No schema migration.** Dedup happens at import time: `HistoryMerge.timestampRange` bounds a `UsageEventDao.getKeysInRange` projection (4 columns, only the window the file covers) into a set, `selectNew` filters, `UsageRepository.insertEvents` inserts the whole list in ONE DAO call — one `@Insert` call is one Room transaction, and that atomicity is load-bearing: dedup is by key MEMBERSHIP, so a crash that persisted only part of an import would make every later re-import skip a whole key group, permanently losing the unstored copy of a legitimate intra-file duplicate (pinned by `UsageRepositoryInsertEventsTest`). `ImportRulesUseCase.newHistoryEvents` is shared by `preview` and `execute`, and execute RE-READS rather than trusting the preview's number.
- **History skips are counted separately from rule skips** (`invalidHistoryCount`/`invalidHistoryReasons` vs `invalidCount`/`invalidReasons`), with the same per-ENTRY isolation as issue #20 — one corrupt event never costs the user their rules, and a corrupt history array must not read as "20 of your rules could not be imported". History type checks are EXACT (`opt(key) as? T`), not org.json's coercing `getString`/`optBoolean`: coercion diverges between Android and the desktop org.json the unit tests run against, and a `"wasBlocked": "yes"` silently coerced to `false` would be a WRONG stat row rather than a skipped one. The "nothing was importable" envelope error now also considers history — a file whose rules are all unreadable but whose history restores cleanly is not a total failure.
- **UI**: the preview dialog adds `Includes N history event(s) (M new).`; the result dialog adds `History events restored` / `History already present` / `History could not be read` as three distinct lines. A file with NO history says nothing about history, so a pre-history backup reads exactly as it always did (pinned in `ImportMessagesTest`). `buildImportPreviewMessage` takes `ImportPreview` (parse result + new-history count) rather than `ImportResult`.
- **Tests**: `HistoryExportTest` (17 — round trip, escaping, compactness plus a 10k-event bytes-per-event ceiling, v1-without-history, unknown-key tolerance, non-array `history`, the malformed-entry corpus, blocked/walked-away counts preserved), `HistoryMergeTest` (14 — every key axis, ranges, partial overlap, walk-away vs show, intra-file duplicates), `ImportedHistoryInsightsTest` (4 — the real `InsightsCalculator` over the source corpus vs the restored one must be EQUAL for both pages and both ranges), plus history cases in `ImportRulesUseCaseTest` (idempotent re-import, partial overlap, bounded range read) and `ImportMessagesTest`.

### App SETTINGS ride in the same file (optional `settings` key, still version 1)

An export also carries the user's app-level SETTINGS — the custom overlay message pools, the content filter's switch/mode/strict-keyword toggle, Strict Mode's switch and challenge difficulty, and the daily-pass escape hatch — so restoring a backup restores the Nudge the user actually configured, not just its rules. Nine keys ride: `customDelayTitles`, `customDelaySubtitles`, `customHardBlockMessages`, `contentFilterEnabled`, `contentFilterMode`, `contentFilterStrictKeywords`, `strictModeEnabled`, `strictModeChallengeLength`, `emergencyPassEnabled`.

- **Still envelope `version: 1`, for the same reason `history` is.** The new `settings` object is a top-level key added at the existing version, not a version bump: every shipped importer reads the envelope by KNOWN KEY ONLY, so an older Nudge simply ignores an object it doesn't recognise, whereas bumping the version would make every OLDER Nudge reject the whole file as "newer than supported" — costing the user their RULES in order to deliver settings that build could never have applied anyway.
- **Two-level failure policy, one level under `history`'s.** A `settings` key that is PRESENT but not an object fails the whole envelope loudly (`objectOrNull` throws), identical to how `rules`/`groups`/`history` already treat a wrong-shaped top-level key — a key of the wrong SHAPE is evidence about the entire file, not about one entry. A single unreadable KEY *inside* the object, though, is skipped and counted in its own pair of counters (`invalidSettingsCount` / `invalidSettingsReasons`) and never fails the import — issue #20's per-entry-isolation shape, one level down from rules and groups.
- **Absence is the forward-compat mechanism at the key level.** A key simply not present in the JSON means "this file does not carry that setting," and the importing device keeps its own value untouched — which is exactly what lets a backup written by a future Nudge that adds a tenth setting still restore this build's other nine, and what lets a file written by this build restore cleanly on that future one. `settingsJson` only ever WRITES a key it has a value for (`?.let { put(...) }`), never a JSON `null` — null and absent would otherwise mean the same forward-compat thing on the wire, with no way to tell "not carried" from "carried as empty."
- **An empty string in a message pool is a real value, not "absent."** `customDelayTitles` / `customDelaySubtitles` / `customHardBlockMessages` are one message per line, and `""` is how a user who cleared their custom messages is stored — `NudgeMessages.resolvePool` reads that as "use the built-in defaults." Only a genuinely MISSING key means "don't touch this."
- **`GLOBAL_ENABLED` is excluded on purpose, not by oversight.** The device-local settings (`ONBOARDING_COMPLETE`, `EMERGENCY_PASS_USAGE`, `PIP_ESCAPE_PROMPTED`, `DEBUG_LOGGING_ENABLED`) are easy exclusions — they describe this phone, not the user's configuration. The master on/off switch is the harder call: a fresh install already defaults to `true`, so a file carrying `true` restores nothing, while a file carrying `false` would silently turn the whole blocker off on the new device — the failure class this codebase treats as its worst ("a blocker silently blocking nothing"). The only behaviour including it would add is a file's ability to disable protection, so it stays out.
- **Security: import must not become a Strict Mode bypass.** An export file is plain, hand-editable JSON — without a gate, typing `"strictModeEnabled": false` into a text editor would be a one-tap way out of the commitment lock, on the one write path that bypasses the Settings screen entirely. `domain/lock/ImportedSettingsWeakening` is the policy (pure, sibling of `RuleWeakening` and `SettingsWeakening`; it reuses `RuleWeakening.modeStrength`, now `internal`, for the content-filter mode axis rather than re-deriving a strength ladder). `ImportRulesUseCase.weakensProtection` reads LIVE preferences — not anything captured at preview time, because the user can change a setting between seeing the preview dialog and confirming it — and asks the policy whether the incoming file weakens ANY axis: Strict Mode on→off, the challenge length lowered, the emergency pass off→on, the content filter on→off, its strict-keyword sub-toggle on→off, or its block mode softened. The custom message pools are deliberately NOT an axis — they change what the overlay SAYS, never what it blocks or for how long.
- **`ActiveRulesViewModel.confirmImport` gates the WHOLE import, not just the settings step**, through the existing `StrictModeGate` — the same call shape `toggleAppEnabled` already uses. Gating only the settings write would leave rules and history applied while settings sat behind a dialog: a half-applied import. Failing the whole thing closed until the challenge is solved is the same discipline the rest of Strict Mode uses.
- **A second, independent hardening layer for the challenge length itself.** `StrictModeChallenge.MAX_LENGTH` (= `LENGTH_HARD`, 48) range-checks an imported `strictModeChallengeLength` regardless of whether the import is flagged as weakening — a hand-edited file could otherwise install a 100,000-character challenge, which is not a stricter lock, it's a permanent lockout, and it would violate Strict Mode's own invariant that the challenge is always solvable. The value never passes through the app's own difficulty picker on this path, so the cap has to live in code rather than in trusting the UI.
- **All-or-nothing, same discipline as the history restore.** `NudgePreferences.applyImportedSettings` writes every carried key inside ONE `dataStore.edit {}` — a single DataStore transaction — so a mid-write failure cannot land the device between two consistent states (e.g. Strict Mode off with the old challenge length still on file). Settings are applied in `ImportRulesUseCase.execute` AFTER rules (which protect the user) and BEFORE history (which only feeds statistics) — protection first, stats last.
- **UI**: the preview dialog gains "Also restores app settings, replacing this device's." when the file carries a `settings` object; the result dialog gains "App settings restored" and, when any key was unreadable, "Settings that could not be read: N" as its own line — the same separate-counter discipline history skips already established. A file with no settings says nothing about settings, so a pre-settings backup reads exactly as it always did.
- **Tests**: `SettingsExportTest` (24 — the FORMAT contract: round trip field for field, settings+rules+history in one file, escaping, a v1 file without `settings` and an explicitly-null one, an empty/all-unreadable object treated as absent, unknown keys inside `settings` tolerated, a non-object `settings` failing loudly, per-key isolation with the reason naming the key, settings skips counted apart from rule and history skips, every real `BlockMode` accepted as a content-filter mode and `TELEPORT` refused, the challenge-length range check accepted at 12/24/48/`MAX_LENGTH` and refused at 0/-5/100000, plus **a closing brace inside a CUSTOM MESSAGE vs. the history splice** — free text the user types is a far likelier source of a stray `}` than a package name ever was); ### Import fails per-ENTRY, never per-FILE (fixes #20)

Fix for [#20](https://github.com/astraedus/nudge/issues/20). `importRules` mapped eagerly over the rules array, so the first unparseable entry threw out of the loop and the catch returned an empty list: **one bad rule silently discarded every rule AND every group in the file** — on the app's only backup path. The `BlockMode.NONE`-missing-from-the-whitelist trigger was fixed earlier (whitelist now derived from `BlockMode.entries`); this fixes the failure *shape*, which is what generalizes to the next unexpected field.

- **`parseEach(array, label, skipped, parse)`** parses each element in its own `try`, appending `"Rule 3: <reason>"` to a shared `skipped` list instead of aborting. Rules and groups both go through it, so the two can never drift in how tolerant they are. It catches exactly what the envelope handler catches (`JSONException`, `IllegalArgumentException`) — the two ways a malformed entry can fail.
- **`ImportResult.invalidCount` / `.invalidReasons`** carry the skips (the reason strings are capped at 20 — they are display material driven by file content, so `invalidCount` is the authoritative total, never `invalidReasons.size`); `ImportOutcome` passes them to the UI and renames `skippedCount` → **`duplicateCount`**. The two are deliberately separate: a duplicate was understood and intentionally not re-added, an invalid entry is something the user LOST from their backup. Merging them into one "skipped" number would hide the data loss the issue is about.
- **The envelope still fails loudly.** Not JSON, bad version, a `rules`/`groups` key that is present but not an array (`arrayOrEmpty` throws — absent/null is still legitimately "none"), and — the subtle one — **a file where nothing at all was importable**: skipping every entry returns an `error`, never a cheerful "Imported: 0". An empty-but-well-formed backup (a user with no rules) is still a success.
- **Validation added**: a group with a blank name is invalid (it would otherwise create an unnamed group).
- **UI**: `ui/screens/rules/ImportMessages.kt` — `buildImportPreviewMessage` / `buildImportOutcomeMessage` are pure so the disclosure wording is JVM-tested, not eyeballed on a device. The preview warns *before* writing ("2 entries could not be read and will be left out:" + up to 3 reasons); the result dialog reports "Skipped (could not be read): N" separately from duplicates. Extracting them also fixed a string-concat precedence bug (`… else "" + "?\n\n…"`) that dropped the trailing sentence from the preview whenever the file contained groups.
- **Tests**: `ImportSkipInvalidTest` (16 — mixed file, missing/wrong-typed fields, non-object elements, unknown schema junk tolerated, invalid groups, all-invalid, reason capping, envelope shapes), `ImportRulesUseCaseTest` (6 — real `RuleExporter` + mockk repo, asserts what actually reaches the DB and that the three counts are independent), `ImportMessagesTest` (6 — the wording). 13 of these fail against the pre-fix eager parse (verified by reverting the parse loop and re-running).


## Database migration 8→9 (the recreate)

8->9 is the only migration that is not an `ALTER TABLE … ADD COLUMN`: SQLite before 3.35 has no `DROP COLUMN` and minSdk 26 ships far older engines, so it is a create/copy/drop/rename recreate of `usage_events`. Two constraints on anyone touching it — the recreated table must match Room's generated schema for `UsageEvent` byte for byte (`` `id` INTEGER PRIMARY KEY AUTOINCREMENT NOT NULL ``, …) or Room's validation throws on the next open; and the ROWS are user data (the block/allow history behind the stats screen), so they are copied across, never dropped. The column itself had no write path at all — every reader that summed it read 0 forever, which is how the #14 daily-limit bug shipped — so `NudgeDatabaseMigrationTest` also asserts reflectively that `UsageEvent` declares no duration-shaped field, and it cannot come back.
